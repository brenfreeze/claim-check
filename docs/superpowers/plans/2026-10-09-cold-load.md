# Cold-Load Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring `OnDeviceDecimaEngine` cold load under the Phase 0 target of ≤ 3 s. It currently measures 3.5–4.1 s on the emulator.

**Architecture:** The cold-load profile is read 0.7–0.8 s, JSON parse 0.14 s, tokenizer build 2.1–2.6 s, encoder session 0.45–0.65 s, scorer 0.04 s.
1. The tokenizer build is almost entirely `@huggingface/tokenizers`' Unigram constructor building a `CharTrie` over all 250,002 vocabulary pieces: about 1M `Map` nodes. On Node that's 1.6 of 1.8 s and about 100 MB of heap. Replace the trie with a prefix search over the `tokens_to_ids` Map the constructor already builds. Pieces are at most 16 code points long, so check substrings of length 1..16 in increasing order, which is the same order the trie yields them. The patch goes in via patch-package, the same mechanism already used for onnxruntime-react-native.
2. `OnDeviceDecimaEngine.load` runs every stage in sequence. Start both ORT session creations, which run on a native thread, before reading and building the tokenizer on the JS thread, then await everything.
3. Re-measure on the emulator.

**Tech Stack:** TypeScript, Jest + ts-jest, onnxruntime-node 1.24.3 (tests), onnxruntime-react-native 1.24.3 (app), `@huggingface/tokenizers` 0.2.0, patch-package, Expo SDK 57 / RN 0.86 / Hermes, Android emulator.

**Spec:** `~/Downloads/PRD Phase 0 — On-Device Decima Spike.md` (SP-03 tokenizer parity, SP-07 timings; cold-load target ≤ 3 s) and `docs/phase0-results.md` (measured baseline).

- [ ] **Step 3: Patch the Unigram constructor and prefix search in both dist files**

In `node_modules/@huggingface/tokenizers/dist/tokenizers.mjs` and `.../tokenizers.cjs`, inside `var Unigram = class extends TokenizerModel_default {`:

Replace

```js
    this.trie = new CharTrie_default();
    this.trie.extend(this.vocab);
```

with

```js
    // claim-check: trie-free unigram — the 250k-piece CharTrie cost ~1.6 s and ~100 MB to build on every load.
    // Prefix search below walks tokens_to_ids for substrings up to the longest piece instead (same results, same order).
    this.max_piece_chars = 0;
    for (const piece of this.vocab) {
      let n = 0;
      for (const _ of piece) n++;
      if (n > this.max_piece_chars) this.max_piece_chars = n;
    }
```

and in `populate_nodes(lattice)` replace

```js
      const prefixed_tokens = this.trie.common_prefix_search(chars, begin_pos);
```

with

```js
      const prefixed_tokens = [];
      let prefix = "";
      const end = Math.min(chars.length, begin_pos + this.max_piece_chars);
      for (let i = begin_pos; i < end; ++i) {
        prefix += chars[i];
        if (this.tokens_to_ids.has(prefix)) prefixed_tokens.push(prefix);
      }
```

This yields exactly the vocabulary pieces that are prefixes of `chars[begin_pos:]`, shortest first, which is the trie's yield order. `chars` is the lattice's code-point array, so lengths are in code points, the same unit as `max_piece_chars`.

Check no other code in the files references `.trie` (`grep -n "\.trie" node_modules/@huggingface/tokenizers/dist/tokenizers.{mjs,cjs}` should show nothing else that runs for Unigram). If another model class, such as BPE or WordPiece, uses `CharTrie`, leave it alone.

- [ ] **Step 2: Implement overlapped load**

Replace the body of `static async load(...)` in `src/engine/OnDeviceDecimaEngine.ts` with:

```ts
  static async load({ ort, modelDir, readText, sessionOptions, sessionPath = (p) => p }: LoadOptions): Promise<OnDeviceDecimaEngine> {
    const t0 = now();
    // Session creation runs natively off the JS thread: start both first, then read + build the tokenizer meanwhile.
    const timed = (p: Promise<InferenceSession>) => p.then((s) => ({ s, ms: now() - t0 }));
    const encoderP = timed(ort.InferenceSession.create(sessionPath(join(modelDir, 'encoder.onnx')), sessionOptions));
    const scorerP = timed(ort.InferenceSession.create(sessionPath(join(modelDir, 'scorer.onnx')), sessionOptions));
    const sessions = Promise.all([encoderP, scorerP]);
    sessions.catch(() => {}); // surfaced by the await below; avoids an unhandled rejection while the tokenizer builds

    const [cfgText, tokText, tokCfgText] = await Promise.all([
      readText(join(modelDir, 'decima.json')),
      readText(join(modelDir, 'tokenizer/tokenizer.json')),
      readText(join(modelDir, 'tokenizer/tokenizer_config.json')),
    ]);
    const t1 = now();
    const tokJson = JSON.parse(tokText);
    const tp = now();
    const tok = XlmrTokenizer.fromJson(tokJson, tokCfgText);
    const t2 = now();
    const [encoder, scorer] = await sessions;
    const t3 = now();
    const timings = {
      readFilesMs: t1 - t0,
      tokenizerParseMs: tp - t1,
      tokenizerMs: t2 - tp,
      encoderMs: encoder.ms,
      scorerMs: scorer.ms,
      totalMs: t3 - t0,
    };
    return new OnDeviceDecimaEngine(ort, encoder.s, scorer.s, tok, JSON.parse(cfgText), timings);
  }
```

Update the `LoadTimings` doc comments: `encoderMs` / `scorerMs` become "load start → session ready (overlaps the tokenizer stages)", and `totalMs` becomes "wall time".

If the tokenizer stage throws (bad JSON), the session promises may still resolve later. That's acceptable for the spike. Don't add session cleanup for that path.
